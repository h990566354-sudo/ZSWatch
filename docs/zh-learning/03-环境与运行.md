## 2. Windows、Linux 和硬件各能做什么

| 环境 | 可完成的工作 | 需要补齐的条件 |
| --- | --- | --- |
| 当前 Windows | 源码阅读、Git 管理、文档、代码修改 | 编译工具与 SDK 尚未准备 |
| Windows + Nordic 工具链 | 构建 nRF5340 的真实硬件固件 | nRF Connect、对应工具链与依赖；烧录还需目标板 |
| Linux / Linux VM / WSL2 | 构建和运行 `native_sim`，验证 App、UI 和事件逻辑 | SDK、Linux 编译依赖、SDL2；显示窗口需要可用图形环境 |
| GitHub 上的 Linux runner | 构建与无界面模拟器测试，保存日志和截图 | 自己的 GitHub 仓库、可运行的工作流和依赖下载 |
| WatchDK / 对应版本手表 | BLE、真实传感器、烧录、显示、功耗等实机验证 | 匹配的硬件、固件与必要的调试/测量设备 |

**`zephyr.exe` 和 `zswatch_native_sim_64.exe` 虽然以 `.exe` 结尾，仍是 Linux 程序，不能直接在 Windows 中双击运行。** 官方 native simulator 仅支持 Linux；Windows 可用 Linux VM / WSL2。

WSL2 路线中，Nordic 工具链也要装在 Linux 环境内，不能把 Windows 工具链路径直接拿来编译 Linux 模拟器。建议把用于构建的工作副本放在 Linux 文件系统内，避免跨文件系统的路径、权限和性能问题。图形窗口可用 WSLg；无界面自动化可用 Xvfb。BLE 属于后续独立工作，不应把 Windows 蓝牙设备在 WSL 中自动可用当作前提。

参考：[官方 Linux 模拟器说明](https://zswatch.dev/docs/development/linux_development)、[Zephyr native_sim 文档](https://docs.zephyrproject.org/latest/boards/native/native_sim/doc/index.html)。

## 3. 从源码到完整开发工作区

以下命令是环境准备完成后的执行方案，本轮尚未执行。除特别标明外，均从 ZSWatch 仓库根目录运行；Linux 命令放在 Linux 的 nRF Connect Terminal 中运行。

项目除了主仓库，还包含传感器库、2048 游戏库、音频库和硬件仓库等 Git 子模块。普通 `git clone` 并不意味着这些内容已经完整下载。新下载时可使用递归克隆；已经下载主仓库时补齐：

```bash
git submodule update --init --recursive
```

然后初始化 SDK 工作区：

```bash
west init -l app
west update
python -m pip install -r zephyr/scripts/requirements.txt
python -m pip install -r app/scripts/requirements.txt
```

`west init` 对一个工作区只做一次。若提示工作区已初始化，先检查当前工作区和 manifest，不要反复重新初始化。`west update` 会获取大量依赖，需要网络与足够磁盘空间；主仓库能够下载不代表全部依赖都能下载。

Windows 的官方依赖安装方案对第二行 pip 命令增加 `--no-build-isolation`，用于处理 `pynrfjprog` 的构建环境问题：

```powershell
python -m pip install --no-build-isolation -r app/scripts/requirements.txt
```

官方 CI 另外安装 `nrf/scripts/requirements-build.txt`。这与面向本地开发的文档路径不同，不应只复制某一行就认定所有依赖都已具备。

注意：构建阶段会通过 `app/sysbuild.cmake` 对下载的 Zephyr 和部分子模块应用项目补丁。SDK 应使用该项目自己的工作区，避免与其他项目共用一份会被修改的依赖目录。

## 4. 第一条验收路线：不使用硬件的模拟器

Ubuntu / Debian 的基础显示与编译依赖：

```bash
sudo apt-get update
sudo apt-get install build-essential libsdl2-dev
```

完成上节的 SDK 初始化后，先按官方 CI 的方式构建，使用独立目录并打开测试配置：

```bash
west build app --build-dir app/build_native_learning -p -b native_sim/native/64 -- -DSB_CONF_FILE=sysbuild_no_mcuboot_no_xip.conf -DEXTRA_CONF_FILE=boards/test_mode.conf
```

这里有三个容易忽略的点：

1. 板名完整写为 `native_sim/native/64`。
2. 模拟器使用 `sysbuild_no_mcuboot_no_xip.conf`，不能套用真实板的 MCUboot / 外部闪存 XIP 配置。
3. `boards/test_mode.conf` 跳过首次引导，并增加相关日志，方便自动化检查；它不是功耗优化配置。

构建成功后，图形环境中直接运行：

```bash
./app/build_native_learning/app/zephyr/zephyr.exe
```

屏幕逻辑分辨率为 240×240，native 配置显示为 200% 缩放。鼠标模拟触摸；Enter 确认；Backspace 返回；上、下方向键模拟对应按键。默认 VS Code 调试配置寻找 `app/build/app/zephyr/zephyr.exe`，若使用本方案的独立目录，需要调整调试路径，或直接运行本节的文件。

直接运行不需要开启 BLE。默认的 `Debug Native (sudo)` 调试项会传入 `--bt-dev=hci0` 并操作主机蓝牙，第一次只验收 UI 时先使用直接运行或无 BLE 的自动化测试。

native 配置明确关闭了真实 BMI270、磁力计等硬件驱动，部分数据通过模拟驱动提供。例如麦克风模拟器生成 440 Hz 正弦波，压力与环境光也有模拟配置。因此，模拟器上的显示结果不能证明真实传感器精度、采样稳定性或音频录制质量。

## 5. 第二条验收路线：日志、截图与自动测试

仓库已经提供 `app/pytest/test_native_app.py` 和 `native_sim_runner.py`。`TestNativeSim` 不要求 BLE，包含四类检查：启动、App 启动、截图产生和 App 关闭。

先准备无界面显示与截图工具，然后安装测试依赖：

```bash
sudo apt-get install xvfb imagemagick
python -m pip install -r app/pytest/requirements.txt
mkdir -p ../ZSWatch-evidence/screenshots
```

运行无 BLE 测试，并把结果存到仓库旁边的证据目录：

```bash
python -m pytest app/pytest/test_native_app.py::TestNativeSim -s --app Calc --exe-path app/build_native_learning/app/zephyr/zephyr.exe --screenshot-dir ../ZSWatch-evidence/screenshots --junitxml=../ZSWatch-evidence/native.xml --html=../ZSWatch-evidence/native.html --self-contained-html
```

实际 App 名称由 `application_t.name` 决定，计算器在源码中叫 `Calc`。不要仅根据目录名或文档示例猜测名称。测试代码自动创建 Xvfb、启动固件、查找 shell 伪终端并保存截图。

验收时同时记录：源码提交号、构建命令、依赖版本、测试通过/失败/跳过数量、启动日志、截图和人工操作结果。**如果没有找到可执行文件，这组测试会跳过；“命令正常退出”不能自动算作“测试通过”。**

现成测试的证明力也有边界：App 启动/关闭主要检查没有崩溃，截图测试主要检查文件存在；它们并没有完整断言 App 的业务行为、显示内容或资源释放。完成自己的功能后，应补充实际功能断言，例如输入 → 状态变化 → 显示结果，以及关闭、再打开、休眠、唤醒等生命周期场景。

这套 runner 会清除模拟器保存的 `flash.bin`，并终止残留的 `zephyr.exe` 进程。不要在同一 Linux 环境同时运行多个互相依赖的模拟器会话。测试截图也应人工打开核对，不能仅确认文件存在。

源码参考：[native 测试](https://github.com/ZSWatch/ZSWatch/blob/1d4ad702b5d0242895c409243d4e189f287f9104/app/pytest/test_native_app.py)、[运行器](https://github.com/ZSWatch/ZSWatch/blob/1d4ad702b5d0242895c409243d4e189f287f9104/app/pytest/native_sim_runner.py)。

## 6. 上传自己的 GitHub 后，怎样理解 CI

上游 `build.yml` 在 Ubuntu 24.04 与指定容器中构建五种目标、debug/release 两类矩阵，其中包含 native simulator。模拟器产物被改名为 `zswatch_native_sim_64.exe`。

上游完整 `test.yml` 使用 `self-hosted` runner，连接真实 WatchDK、其他板卡和功耗设备。自己的 Fork 通常没有这些设备和 runner，不能把完整上游 CI 全部成功当成默认结果。

个人项目更适合先建立仅针对 native simulator 的工作流：下载依赖 → 构建 → 执行无 BLE 测试 → 上传日志、JUnit/HTML 报告和截图。待自己真正运行成功后，才在 README 放通过标记。当前只有方案准备，尚未提交或运行这条个人工作流。

## 7. 后续有硬件时：构建、烧录与更新

先确认板卡版本。官方文档列出 WatchDK、Legacy v4/v5；源码 CI 还构建当前 `zswatch@1/nrf5340/cpuapp`。目标字符串必须与手中的板卡匹配，不应看到 nRF5340 就任选一个目标。

以 WatchDK、串口日志为例：

```bash
west build app --build-dir app/build_watchdk_debug -b watchdk@1/nrf5340/cpuapp -- -DEXTRA_CONF_FILE="boards/debug.conf;boards/log_on_uart.conf" -DEXTRA_DTC_OVERLAY_FILE=boards/log_on_uart.overlay
west flash --build-dir app/build_watchdk_debug
```

串口日志需要配套 overlay；RTT 日志使用 `boards/debug.conf;boards/log_on_rtt.conf`，并需要 J-Link。只构建成功可以证明该目标能够编译，不能证明固件已经在实物上运行。

如果设备已经具有 MCUboot 串口恢复功能，可经 USB 更新，无须单独的调试器：连接 USB，按住右下按钮并复位，然后在[官方更新页面](https://zswatch.dev/update)选择 USB Serial 与本地 `dfu_application.zip`。需要更新的三部分分别为内部应用、外部 XIP 应用和网络核固件。首次空白硬件的启动链准备不能直接等同于这种现有设备更新流程。

使用 mcumgr 手动上传时，官方使用三个 image index：内部应用 `1`、外部应用 `5`、网络核 `3`。网络核上传后需等待约 30 秒完成内部复制，再复位。实际端口、板卡与构建产物要按设备确认，不直接照搬示例端口。

参考：[官方编译与烧录说明](https://zswatch.dev/docs/development/compiling)。

## 8. 图片资源为什么要单独处理

native 模拟器把 LVGL 图片 C 文件编译进程序；硬件从外部闪存读取资源。因此，模拟器上新图标正常显示，不代表实机已经具有对应图片。

新增图片时，使用 LVGL v9 图片格式；普通图片用 RGB565，含透明度图片用 RGB565A8。C 源文件放入对应图片目录后，可供 native 构建使用。硬件资源另行生成：

```bash
python app/scripts/lvgl_c_array_to_bin_lvgl9.py app/src/images/icons/my_icon.c app/src/images/binaries/S/
west upload_fs --type raw --generate_only
```

`--generate_only` 只生成资源文件，不需要连接手表。脚本实际生成 `lvgl_resources_raw` 与 `.hex`；CI 再把前者改名为 `lvgl_resources_raw.bin`。看到文档中的 `.bin` 名称时，应区分发布产物和脚本原始输出。

WatchDK 实机使用调试器上传的示例为：

```bash
west upload_fs --type raw --ini_file app/boards/zswatch/watchdk/support/qspi_mx25u51245.ini
```

Legacy v4 使用另一个 QSPI ini 文件，不能混用。也可以在已运行固件中进入 Apps → Update、开启对应传输，再经官方更新页面上传资源。只改固件逻辑而未改变资源时通常不必重复上传；第一次部署或图标变化时需核对资源版本。

参考：[官方图片资源说明](https://zswatch.dev/docs/development/image_resources)、[资源上传脚本](https://github.com/ZSWatch/ZSWatch/blob/1d4ad702b5d0242895c409243d4e189f287f9104/app/scripts/upload_fs_west_command.py)。

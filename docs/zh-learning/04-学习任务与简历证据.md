# ZSWatch：学习任务与简历证据

目标是能独立解释、修改、验证一个功能，再把可核查的个人贡献写进简历。阅读资料和复制仓库都不等于掌握项目。

**当前状态（2026-10-10，文档整理时）：**已下载原项目并开展源码导读；尚未构建、运行、烧录或实现个人功能。个人 GitHub Fork 已创建；本资料随中文学习材料一起整理发布。下文全部阶段与功能都是计划，完成后应补上提交、日志、截图和实际结果。

下文阅读路径均以 ZSWatch 源码仓库根目录为起点。按阶段推进；上一阶段未验收，就先补齐，不按“看过多少文件”判断进度。

## 1．补齐 C 基础，确定项目边界

**阅读：**`README.md` → `app/src/managers/zsw_app_manager.h` → `app/src/events/pressure_event.h` → `app/west.yml`。

**动手：**整理指针、结构体、函数指针、`static`、条件编译与返回值；用小例子定义一个事件结构体和处理回调。画出“原项目已有功能 / 自己准备增加功能”两列，并记录源码提交版本。

**验收：**能解释 `application_t` 的启动/停止回调；能按值复制结构体，并说清局部变量地址何时失效；能区分项目代码、SDK 依赖和工具链。保存自己的讲解笔记。

**面试问题：**为什么使用函数指针管理多个 App？`static` 修饰文件内变量和函数分别有什么作用？

## 2．先复现原项目的 native 基线

**前置：**阶段 1。**阅读：**`website/docs/development/toolchain.md`、`linux_development.md`、`app/west.yml`、`app/boards/native_sim_64.conf`、`app/pytest/test_native_app.py`。

**动手：**按《03-环境与运行》建立 Linux/WSL2 开发环境，构建 `native_sim/native/64`；先采用无 BLE 的运行路径，打开原生 App，退出并重新打开。

**验收：**保存 SDK/源码版本、完整构建结果、启动日志和一张实际截图；明确成功、失败或跳过。输出文件虽然叫 `zephyr.exe`，仍是 Linux 程序，不能当作 Windows 可执行文件。

**面试问题：**`west`、CMake、Kconfig、设备树分别解决什么问题？native 的显示成功能证明哪些能力，不能证明哪些？

## 3．跟踪启动、调度与界面更新

**前置：**阶段 2。**阅读：**`app/src/main.c` → `app/src/ui/zsw_ui_controller.c` → `app/src/events/zsw_periodic_event.c` → `app/src/managers/zsw_app_manager.c`。

**动手：**画出 `main()` 提交 `init_work`、初始化管理器与 UI 的调用顺序；用断点或日志确认工作队列和 UI 更新的执行上下文，记录与自己的预测是否一致。

**验收：**能从入口定位到一次界面刷新；能解释线程、工作队列、定时器的职责，以及为什么耗时操作不应堵住 UI。不要仅凭函数名推断线程归属。

**面试问题：**为什么初始化借用系统工作队列？收到事件后直接操作 LVGL 对象有什么条件和风险？

## 4．掌握一个 App 的完整生命周期

**前置：**阶段 3。**阅读：**`website/docs/development/writing_apps.md` → `app/src/applications/stopwatch/stopwatch_app.c`、`stopwatch_ui.c` → `app/src/managers/zsw_app_manager.h` → `app/src/applications/CMakeLists.txt`、`Kconfig`。

**动手：**在个人开发分支新增最小工具 App：一个数值标签、增加/清零按钮；将界面和业务状态分离，接入注册、启动、停止和构建配置。

**验收：**能从菜单进入，连续开关后行为正常；停止时取消自己的定时器/订阅并释放界面；理解 `UI_VISIBLE`、`UI_HIDDEN`、`STOPPED`，在界面不可用时不访问失效对象。提交可审查的改动。

**面试问题：**App 停止和界面暂时隐藏有什么差别？漏删定时器为何可能在第二次打开时崩溃？

## 5．读通数据采集到事件消费

**前置：**阶段 4。**阅读：**`app/src/sensors/zsw_pressure_sensor.c` → `app/src/events/pressure_event.c`、`.h` → `app/src/applications/sensors_summary/sensors_summary_app.c`；再读 `app/drivers/sensor/bmp581/zsw_bosch_bmp581_emul.c`。

**动手：**分别画出“定时读取并发布 pressure 事件”和“Sensor App 直接调用读取接口”两条路径；注明单位、错误返回、刷新周期。设计独立的模拟数据入口，不假定已有 Sensor App 自动订阅 pressure 事件。

**验收：**能指出哪一层是驱动、封装、事件和界面；用固定输入序列追踪发布与消费，说明无效/过期数据如何处理。数据源必须显示为模拟，不能称为真实采集。

**面试问题：**发布订阅与直接调用如何取舍？读取失败后显示上次值会带来什么歧义？

## 6．完成一个能讲透的个人功能

**前置：**阶段 5。**推荐首选：模拟传感器监测、统计与告警。**在自己的 App 中注入可重复的数据，维护固定容量的滑动窗口，显示当前值、均值、最小/最大值，并实现阈值告警与恢复阈值。第一版用屏幕提示和日志验证。

**阅读：**阶段 4、5 的路径；界面提示参考 `app/src/ui/popup/zsw_popup_window.c`，配置参考 `app/src/applications/sensors_summary/Kconfig`。

**验收：**输入 `10、20、30` 得到均值 `20`、最小值 `10`、最大值 `30`；窗口未满时除以实际样本数。设进入阈值 `25`、恢复阈值 `20`，检查跨越、持续超限、恢复和再次超限，明确去重规则；检查空窗口、无效值、窗口覆盖、关闭/隐藏界面后继续收到数据。留下预期与实际对照。

**面试问题：**为何用固定容量窗口？统计更新复杂度是多少？两个阈值如何避免告警抖动？什么状态需要保留，什么资源必须释放？

另外两个可选方向：

| 方向 | 个人贡献与阅读参考 | native 验证范围与局限 |
|---|---|---|
| 专注计时工具 | 基于 `app/src/applications/timer/` 或 `stopwatch/`，增加工作/休息状态、暂停恢复和进度显示 | 可验证状态迁移与 UI；主机计时结果不能证明真实 RTC 精度、震动效果或休眠唤醒 |
| 单位换算/计算历史工具 | 参考 `app/src/applications/calculator/`；自行实现输入校验、单位换算、有限条历史 | 可验证计算边界与界面；已有计算器核心来自 Zephyr 示例，不能把原有算法列为个人开发 |

native 配置已包含 BMP581、APDS9306 等模拟器，也有显示/输入和模拟存储支持，但并不复现整只手表。个人功能的模拟测试不能证明传感器精度、实际 BLE 配对、真实 Flash 寿命、整机功耗或续航；这些需另建硬件实验并保存测量条件。

## 7．形成可复现的仓库、验证与简历材料

**前置：**阶段 6。**阅读：**`app/pytest/README.md`、`test_native_app.py`、`native_sim_runner.py`、根目录 `LICENSE`。

**动手：**补充关键算法/状态边界验证及 App 启动、关闭、重开验证；在 GitHub 个人仓库保留上游来源、版权与许可证，提交自己的功能、运行说明和结果。无需通知原作者。不要把已有测试文件当成自己的测试成果。

**验收：**他人能按文档找到版本、构建方式、模拟输入、预期行为与证据；每条简历表述能指向自己的提交或实验。自动化测试被跳过时不能记为通过。没有测量就不填写性能提升百分比。

**面试问题：**哪些代码是上游，哪些是自己的？能否现场修改一个阈值并解释影响？曾遇到哪个具体故障，怎样复现和定位？还缺哪些硬件验证？
